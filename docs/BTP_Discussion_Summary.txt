  --------------------
  1. INITIAL CONTEXT
  --------------------

Chirag began by reading the MICRO’25 paper: “Drishti: Do Not Forget
Slicing While Designing Last-Level Cache Replacement Policies for
Many-Core Systems.”

He initially considered extending Drishti by making it explicitly
prefetch-aware. After reaching out to one of the authors (Prerna), it
was clarified that:

-   Drishti is NOT a replacement policy.
-   Drishti is a set of architectural enhancements: • Per-core global
    reuse prediction • Dynamic sampled cache selection
-   Prefetch awareness should come from the underlying replacement
    policy (e.g., Mockingjay).

Thus, modifying Drishti to directly handle prefetches would violate its
design philosophy.

  --------------------------
  2. REFINED BTP DIRECTION

The direction shifted from: “Prefetch-aware Drishti”

To: “Lightweight, Prefetch-Resilient LLC Replacement Policy”

The professor explicitly stated: - Focus on lightweight design -
Prefetch-resilient behavior - Drishti can be explored during the
semester

This means: - Not designing heavy ML-based predictors - Not implementing
full Hawkeye-level complexity - Focus on simple, low-overhead mechanisms

  -----------------------------
  3. IDENTIFIED RESEARCH GAPS
  -----------------------------

Based on literature exploration (Drishti, PACMan, IEEE CAL 2023):

Gap 1: Lack of lightweight, prefetch-resilient replacement designs. Many
prefetch-aware approaches add hardware complexity.

Gap 2: Replacement–prefetch interaction is mostly studied in monolithic
LLCs. Modern processors use sliced LLCs.

Gap 3: Interaction between global reuse prediction and prefetch noise is
unclear.

Gap 4: Dynamic sampled-cache selection under prefetch-heavy workloads is
not well characterized.

Gap 5: Limited guidance on when sophisticated replacement is worthwhile
under aggressive prefetching.

  --------------------------------------------
  5. IMPLEMENTATION PLAN (LIGHTWEIGHT START)
  --------------------------------------------

Initial Safe Implementation:

Low-Priority Insertion for Prefetches

Idea: - Demand blocks → Insert at MRU - Prefetch blocks → Insert at low
priority (near LRU) - If prefetched block is later used → normal
promotion

Benefits: - Minimal hardware overhead - No large predictors - No global
structures - Reduces pollution from useless prefetches

Where to implement in ChampSim: replacement//update_replacement_state()

Modify insertion logic using: - is_prefetch flag

Evaluation Plan: Compare: - Baseline LRU - Modified LRU With: - Prefetch
ON - Prefetch OFF

Metrics: - LLC MPKI - IPC

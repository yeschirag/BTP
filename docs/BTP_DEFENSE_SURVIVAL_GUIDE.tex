\section{The Memory Wall \& Physical Cache Hierarchy}

\subsection{Why Do Microprocessors Need Caches? (The Nanosecond vs Clock Gap)}
To understand cache replacement, one must first appreciate the physical chasm between CPU execution speed and off-chip memory access latency:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{The Core Execution Rate:} A modern high-performance processor core (modeled after Intel Golden Cove or AMD Zen 4) operates at a clock frequency of \textbf{4.0 GHz}. This means a single clock cycle elapses in exactly:
  \begin{equation}
    T_{\text{cycle}} = \frac{1}{4.0 \times 10^9 \text{ Hz}} = 0.25 \text{ nanoseconds} \quad (250 \text{ picoseconds})
  \end{equation}
  Inside the out-of-order execution engine, integer ALUs can execute simple operations (like \texttt{add}, \texttt{sub}, \texttt{shift}) in a single clock cycle (0.25 ns).
  
  \item \textbf{The Off-Chip Memory Sluggishness:} Main memory is implemented using Dynamic Random-Access Memory (DRAM). Accessing an off-chip DDR4-2400 module requires driving electrical signals through the on-die memory controller, across motherboard copper traces, through the DIMM interface, charging capacitive DRAM bitlines, activating row buffers, and routing data back through the memory bus. This physical sequence takes between \textbf{50 to 80 nanoseconds}.
  
  \item \textbf{The Clock Cycle Chasm:} Converting 60 nanoseconds into CPU clock cycles:
  \begin{equation}
    \text{Latency in Cycles} = \frac{60 \times 10^{-9} \text{ s}}{0.25 \times 10^{-9} \text{ s/cycle}} = 240 \text{ CPU clock cycles!}
  \end{equation}
  \item \textbf{The Memory Wall Crisis (Wulf \& McKee, 1995):} If every memory load instruction (\texttt{MOV}, \texttt{LDR}) had to fetch data directly from DRAM, the CPU would spend over \textbf{99\% of its operational life sitting completely stalled}, waiting for memory bus transactions to complete. CPU computing throughput would be entirely throttled by DRAM bus latency, rendering multi-gigahertz execution units useless.
\end{itemize}

\subsection{The On-Chip Multi-Level Cache Solution}
To hide this brutal latency, chip architects implement a hierarchical pyramid of Static RAM (SRAM) storage directly on the silicon die:
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Level 1 Instruction Cache (L1I) \& Data Cache (L1D):}
  \begin{itemize}
    \item \textbf{Capacity:} 32 Kilobytes each per core.
    \item \textbf{Latency:} 4 to 5 clock cycles ($\sim$1 nanosecond).
    \item \textbf{Design Philosophy:} Extremely fast, tightly coupled to the processor pipeline execution stages. Private to each individual core.
  \end{itemize}

  \item \textbf{Level 2 Cache (L2):}
  \begin{itemize}
    \item \textbf{Capacity:} 512 Kilobytes per core.
    \item \textbf{Latency:} 10 to 14 clock cycles ($\sim$2.5 to 3.5 nanoseconds).
    \item \textbf{Design Philosophy:} Acts as a secondary shock absorber for private L1 misses. Houses aggressive core-level hardware prefetchers.
  \end{itemize}

  \item \textbf{Level 3 / Last-Level Cache (L3 / LLC):}
  \begin{itemize}
    \item \textbf{Capacity:} 8 Megabytes (in our 4-core system, 2MB per core slice).
    \item \textbf{Latency:} 20 to 25 clock cycles ($\sim$5 to 6.25 nanoseconds).
    \item \textbf{Design Philosophy:} \textbf{Physically or logically shared across ALL processor cores}. It serves as the final on-chip defense before a memory request is forced to travel off-chip across the slow DRAM memory bus.
  \end{itemize}
\end{enumerate}

\subsection{Cache Inclusion Properties: Inclusive vs Non-Inclusive vs Exclusive}
A senior professor will almost certainly grill you on how your Last-Level Cache interacts with private L1 and L2 caches. There are three fundamental architectural inclusion paradigms:

\begin{defensebox}[title=\textbf{Inclusion Paradigms Explained}]
\begin{enumerate}[leftmargin=1.2em]
  \item \textbf{Strictly Inclusive LLC:}
  \begin{itemize}
    \item \textit{Rule:} Any cache line present in private L1 or L2 \textbf{must also reside} in the shared LLC.
    \item \textit{Advantage:} Simplifies cache coherence snooping. If an external core wants to know if an address is cached on-chip, it only checks the shared LLC directory.
    \item \textit{Fatal Flaw:} \textbf{Back-Invalidation Storms}. If the LLC evicts a line to make room for a new prefetch, it MUST send a back-invalidation probe up to the private L1 and L2 caches to forcibly evict that line from the core. Prefetch pollution in an inclusive LLC will destroy active L1/L2 working sets!
  \end{itemize}

  \item \textbf{Strictly Exclusive LLC:}
  \begin{itemize}
    \item \textit{Rule:} A cache line resides in EITHER L1/L2 OR the LLC, but \textbf{never in both simultaneously}.
    \item \textit{Advantage:} Maximizes total on-chip storage capacity ($C_{\text{total}} = C_{L1} + C_{L2} + C_{LLC}$).
    \item \textit{Disadvantage:} Every L2 eviction requires an explicit swap writeback into the LLC, consuming immense interconnect crossbar bandwidth.
  \end{itemize}

  \item \textbf{Non-Inclusive / Victim LLC (Our Modeled Hierarchy - AMD Zen / Intel Modern):}
  \begin{itemize}
    \item \textit{Rule:} A line present in L1/L2 \textbf{may or may not} reside in the LLC.
    \item \textit{Advantage:} When the LLC evicts a line, \textbf{it does NOT back-invalidate the L1/L2 caches}. This insulates private core caches from catastrophic replacement churn. Modern high-core processors overwhelmingly favor non-inclusive LLCs.
  \end{itemize}
\end{enumerate}
\end{defensebox}

\section{Microarchitecture of Modern Out-of-Order (OoO) Processors}

Many students fail because they speak about caches as isolated storage boxes without understanding the execution pipeline feeding them. Let us dissect what is happening inside the CPU core.

\subsection{The Instruction Pipeline: Why Memory Stalls Kill IPC}
Our ChampSim simulation models a high-performance Out-of-Order (OoO) superscalar core with 6-wide issue and a 256-entry Reorder Buffer (ROB).

\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Fetch \& Branch Prediction:} The instruction fetch unit fetches 6 instructions every cycle from L1I. The \textbf{Hashed Perceptron Branch Predictor} predicts the direction of conditional branch instructions (\texttt{if}, \texttt{else}, \texttt{for}). The \textbf{Branch Target Buffer (BTB)} caches the target jump addresses.
  \item \textbf{Decode \& Register Rename:} Instructions are decoded into micro-operations ($\mu$ops). Architectural registers (\texttt{RAX}, \texttt{RBX}) are dynamically renamed onto physical register files to eliminate false dependencies (Write-After-Write, Write-After-Read).
  \item \textbf{Dispatch to Reorder Buffer (ROB):} The instructions are placed in program order into the \textbf{256-entry ROB}. The ROB guarantees precise exception handling and ensures that instructions commit in strict program order, even though they execute out of order.
  \item \textbf{Issue \& Out-of-Order Execution:} Once an instruction's input data operands become available, the reservation stations issue the instruction to an ALU, FPU, or Load/Store Unit, regardless of program order.
  \item \textbf{Commit / Retire:} Once an instruction finishes execution and reaches the head of the ROB, it commits its architectural state to the register file and leaves the pipeline.
\end{enumerate}

\begin{trapbox}
\textbf{The Deadly Professor Trap:}\\
\textit{``Why does a single LLC cache miss cause IPC to collapse from 2.2 down to 0.08? Can't the out-of-order execution engine just execute other instructions around the miss?''}
\end{trapbox}

\begin{answerbox}
\textbf{The Exact Scientific Explanation (ROB Blocking \& Head-of-Line Stall):}\\
``Sir, an Out-of-Order core has a finite Reorder Buffer window---in our model, \textbf{256 instructions}. When an instruction at the head of the ROB experiences an LLC cache miss, it must wait $\sim$240 clock cycles for DDR4 main memory to return data. 

While that load is stalled at the head of the ROB, the execution engine continues issuing and executing independent instructions downstream. However, because instructions MUST commit in strict program order, none of these subsequent instructions can commit. Within 40 to 60 clock cycles, all 256 entries of the ROB fill up with executed instructions waiting for the head instruction to finish. 

Once the ROB is full, the dispatch stage stalls completely. The decode, rename, and fetch stages back-pressure and freeze. The entire 6-wide core sits completely paralyzed for the remaining 180 clock cycles. This is known as an \textbf{ROB Head-of-Line Blocking Stall}. This is why memory misses destroy IPC!''
\end{answerbox}

\subsection{Miss Status Holding Registers (MSHRs): The Hidden Bottleneck}
Caches do not process misses instantaneously. When a memory access misses in the cache:
\begin{itemize}[leftmargin=1.5em]
  \item The cache cannot block all incoming accesses while waiting for DRAM; it must remain \textbf{non-blocking}.
  \item To remain non-blocking, the cache controller allocates an entry in an \textbf{MSHR (Miss Status Holding Register)}.
  \item The MSHR tracks: the memory address, the destination register, the requesting core ID, and secondary requests arriving for the same in-flight cache line.
  \item \textbf{The MSHR Capacity Limit:} In ChampSim, each cache level has a finite pool of MSHRs (e.g., 32 entries at L2, 64 entries at LLC).
  \item \textbf{MSHR Exhaustion Stall:} If an aggressive prefetcher issues 64 inaccurate prefetch requests for lines that are not in cache, \textbf{every single MSHR entry is consumed by garbage prefetches}. When a real demand load instruction from the CPU arrives, the cache has no free MSHRs to service it. The CPU pipeline must immediately stall at the memory execution unit. \textbf{Inaccurate prefetchers do not just waste cache capacity; they starve memory controller queues and exhaust MSHR slots!}
\end{itemize}

\section{Cache Anatomy, Addressing Mathematics \& Associativity}

\subsection{Physical Memory Address Decomposition}
A senior professor will ask you to draw the address breakdown on the whiteboard. Here is the exact binary mathematics for our simulated memory system:

\begin{defensebox}[title=\textbf{Address Decomposition Parameters}]
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Total LLC Capacity ($C$):} 8 Megabytes $= 8 \times 1024 \times 1024 \text{ Bytes} = 8,388,608 \text{ Bytes} = 2^{23} \text{ Bytes}$.
  \item \textbf{Cache Line / Block Size ($B$):} 64 Bytes $= 2^6 \text{ Bytes}$.
  \item \textbf{Associativity / Number of Ways ($W$):} 16 ways per set.
  \item \textbf{Physical Address Width ($A$):} 64-bit architecture (ChampSim models 64-bit virtual addresses mapped to physical memory).
\end{itemize}
\end{defensebox}

\subsubsection{Step-by-Step Mathematical Derivation}
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Block Offset Bits ($b$):}
  Determines the exact byte location within a 64-Byte line:
  \begin{equation}
    b = \log_2(\text{Block Size}) = \log_2(64) = 6 \text{ bits} \quad (\text{Address Bits } [5:0])
  \end{equation}

  \item \textbf{Capacity per Set ($S_{\text{bytes}}$):}
  Since each set contains 16 ways of 64 Bytes each:
  \begin{equation}
    S_{\text{bytes}} = W \times B = 16 \times 64 = 1,024 \text{ Bytes} = 1 \text{ Kilobyte} = 2^{10} \text{ Bytes}
  \end{equation}

  \item \textbf{Number of Sets ($N_{\text{sets}}$):}
  Dividing total cache capacity by the size of one set:
  \begin{equation}
    N_{\text{sets}} = \frac{C}{S_{\text{bytes}}} = \frac{8,388,608 \text{ Bytes}}{1,024 \text{ Bytes/set}} = 8,192 \text{ Sets} = 2^{13} \text{ Sets}
  \end{equation}

  \item \textbf{Set Index Bits ($s$):}
  The number of bits required to uniquely select one of the 8,192 sets:
  \begin{equation}
    s = \log_2(8,192) = 13 \text{ bits} \quad (\text{Address Bits } [18:6])
  \end{equation}

  \item \textbf{Tag Bits ($t$):}
  The remaining upper bits identifying whether the stored line matches the requested memory page:
  \begin{equation}
    t = 64 - s - b = 64 - 13 - 6 = 45 \text{ bits} \quad (\text{Address Bits } [63:19])
  \end{equation}
\end{enumerate}

\begin{center}
\small
\begin{tabular}{|c|c|c|}
\hline
\textbf{Tag Field (45 bits)} & \textbf{Set Index Field (13 bits)} & \textbf{Block Offset Field (6 bits)} \\
Bits $[63 : 19]$ & Bits $[18 : 6]$ & Bits $[5 : 0]$ \\
Identifies unique block in memory & Selects 1 of 8,192 Sets in LLC & Selects byte within 64B line \\
\hline
\end{tabular}
\end{center}

\subsection{Why 16-Way Set Associativity? (The Engineering Trade-Off)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Direct-Mapped ($W=1$):} Each address maps to exactly 1 slot. Ultra-fast lookup (zero comparator delay), but catastrophic \textbf{conflict misses}. If two active memory addresses happen to share the same index bits $[18:6]$, they constantly evict each other in an infinite thrashing loop.
  \item \textbf{Fully Associative ($W = \text{Total Lines}$):} Any address can sit in any slot. Eliminates conflict misses completely, but requires 8,192 simultaneous parallel tag comparisons using power-hungry Content-Addressable Memory (CAM). Unfeasible for large caches due to silicon area, routing congestion, and thermal dissipation.
  \item \textbf{16-Way Set-Associative (The Industry Standard):} Hits the optimal Pareto frontier: provides 16 alternative slots per set to virtually eliminate conflict misses, while requiring only 16 parallel tag comparators per access, easily meeting 20-cycle timing constraints.
\end{itemize}

\section{Demystifying the Benchmarks: What GCC, MCF, Perl, and OMNeT++ Actually Do}

\begin{trapbox}
\textbf{The Professor's Favorite Attack:}\\
\textit{``You show results for gcc, mcf, perlbench, and omnetpp. What do these programs actually do? What algorithms are running inside them? Why did you pick them? If you don't even know what these programs compute, your simulation results are completely meaningless!''}
\end{trapbox}

This section gives you an exhaustive, algorithmic breakdown of each benchmark so you can answer with absolute authority.

\subsection{What is SPEC CPU?}
The \textbf{Standard Performance Evaluation Corporation (SPEC)} is the non-profit industry consortium formed by Intel, AMD, IBM, ARM, Apple, and leading universities to create standardized, vendor-neutral hardware benchmark suites. SPEC CPU 2006 and SPEC CPU 2017 are the universal gold standard for evaluating microarchitectural innovations in top-tier conferences (ISCA, MICRO, HPCA, ASPLOS).

\subsection{What is a SimPoint and Pinned Trace?}
SPEC benchmarks take hours to run, executing \textbf{trillions of instructions}. Simulating 1 trillion instructions in a cycle-accurate software simulator at 50,000 instructions per second would take \textbf{231 days of continuous execution}!

To solve this, researchers at UC San Diego developed \textbf{SimPoint}:
\begin{itemize}[leftmargin=1.5em]
  \item SimPoint profiles the execution of the entire program and vectors Basic Block Frequencies (BBVs).
  \item Using machine-learning clustering ($k$-means), SimPoint mathematically identifies representative 20M--100M instruction phases (SimPoints) whose microarchitectural behavior (cache miss rate, branch misprediction rate, IPC) matches the full multi-trillion instruction run with $>98\%$ statistical fidelity.
  \item In our study, we use official \textbf{pinned SimPoint traces} from the CRC cache competition.
\end{itemize}

\subsection{Benchmark 1: \texttt{403.gcc} (GNU C Compiler)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Real-World Function:} It is the official GNU C Compiler (version 3.2.2) compiling pre-processed C source code files into optimized assembly/machine code.
  \item \textbf{Underlying Algorithms:}
  \begin{itemize}
    \item Lexical analysis, syntax parsing, and Abstract Syntax Tree (AST) construction.
    \item Static Single Assignment (SSA) optimizations and dead-code elimination.
    \item Register allocation via Chaitin-Briggs Graph Coloring.
  \end{itemize}
  \item \textbf{Microarchitectural Behavior:}
  \begin{itemize}
    \item \textbf{Instruction Locality:} High branch frequency with complex nested conditional logic. Heavily exercises the branch predictor and BTB.
    \item \textbf{Memory Access Pattern:} Moderate working set size. Frequently traverses structured arrays and contiguous compiler symbol tables.
    \item \textbf{Hardware Prefetcher Behavior:} \textbf{Highly Accurate ($>50-60\%$)}. The L2 stride prefetcher easily detects sequential sweeps across parse trees and array buffers, prefetching lines well in advance.
    \item \textbf{Execution Profile:} Compute-bound, high pipeline utilization, baseline IPC around \textbf{2.14 to 2.18}.
  \end{itemize}
\end{itemize}

\subsection{Benchmark 2: \texttt{429.mcf} (Combinatorial Vehicle Scheduling)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Real-World Function:} Solves large-scale single-depot vehicle scheduling problems in public transit networks. It plans bus schedules to minimize operational costs under route and timetable constraints.
  \item \textbf{Underlying Algorithms:}
  \begin{itemize}
    \item Formulated as a Minimum-Cost Flow problem on a directed graph.
    \item Solved using the \textbf{Network Simplex algorithm}.
    \item Core data structures are massive pointer-linked trees of nodes and arcs:
    \begin{verbatim}
    typedef struct node {
        cost_t          potential;
        struct node     *parent;
        struct node     *first_child;
        struct node     *sibling;
        struct arc      *pred;
    } node_t;
    \end{verbatim}
  \end{itemize}
  \item \textbf{Microarchitectural Behavior (The Cache Architect's Worst Nightmare):}
  \begin{itemize}
    \item \textbf{Memory Access Pattern:} Constant, unbridled \textbf{pointer chasing}. During tree pivots and dual variable updates, the algorithm executes instructions like:
    \begin{verbatim}
    node = node->parent;
    sibling = node->first_child->sibling;
    \end{verbatim}
    Each pointer dereference jumps to a pseudo-random address across hundreds of megabytes of heap memory.
    \item \textbf{Hardware Prefetcher Behavior:} \textbf{Catastrophic Failure ($<1\%$ Accuracy)}. The hardware stride prefetcher sees misses at disparate addresses, attempts to calculate false strides, and floods the memory controller and LLC with thousands of speculative requests that are \textbf{never accessed}.
    \item \textbf{Execution Profile:} Memory-stall bound. LLC miss rate exceeds \textbf{85\%}. ROB entries are permanently stalled waiting for DRAM. Baseline IPC collapses to \textbf{0.08 to 0.09}.
  \end{itemize}
\end{itemize}

\subsection{Benchmark 3: \texttt{600.perlbench\_s} (Perl 5 Interpreter)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Real-World Function:} A real Perl 5.28 interpreter executing production scripts, specifically processing mail through SpamAssassin, parsing HTML, and executing regex transformations.
  \item \textbf{Underlying Algorithms:}
  \begin{itemize}
    \item Perl hash table insertions, bucket collisions, and lookups (\texttt{HV} structures).
    \item Dynamic string manipulation and memory allocation for variable scalars (\texttt{SV}).
    \item Regular expression pattern matching state machines.
  \end{itemize}
  \item \textbf{Microarchitectural Behavior:}
  \begin{itemize}
    \item \textbf{Memory Access Pattern:} Balanced profile with fine-grained heap allocations and hash lookups. Moderate spatial and temporal locality.
    \item \textbf{Execution Profile:} Instruction-level parallelism is moderately high. Sensitive to LLC capacity. Baseline IPC sits around \textbf{1.95 to 2.02}.
  \end{itemize}
\end{itemize}

\subsection{Benchmark 4: \texttt{471.omnetpp} (Discrete Event Network Simulator)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Real-World Function:} A discrete event simulation engine modeling large-scale computer communication networks (Ethernet protocols, queuing networks, MAC-layer packet routing).
  \item \textbf{Underlying Algorithms:}
  \begin{itemize}
    \item Maintains a central \textbf{Future Event Set (FES)}, implemented using balanced binary search trees and calendar priority queues.
    \item Dequeues the event with the earliest simulation timestamp, executes protocol state changes, and inserts new speculative future events into the priority queue.
  \end{itemize}
  \item \textbf{Microarchitectural Behavior:}
  \begin{itemize}
    \item \textbf{Memory Access Pattern:} Irregular pointer traversals across event queues interspersed with small buffer copies.
    \item \textbf{Hardware Prefetcher Behavior:} Mixed accuracy ($15-25\%$).
    \item \textbf{Execution Profile:} Highly latency-sensitive. Stalls in the LLC cause queuing delays that back-pressure the simulation loop. Baseline IPC is around \textbf{0.28 to 0.32}.
  \end{itemize}
\end{itemize}

\subsection{Why This 4-Core Mix (\texttt{gcc + mcf + perlbench + omnetpp}) is the Ultimate Stress-Test}
In academic research, testing 4 identical compute cores running \texttt{gcc} reveals nothing about cache contention because all cores have predictable, well-behaved memory access.

Our 4-core heterogeneous mix is deliberately constructed to represent the \textbf{worst-case shared multicore contention scenario}:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Core 0 (\texttt{gcc}) \& Core 2 (\texttt{perlbench}):} Two high-throughput compute threads that demand low LLC latency and clean cache lines to sustain IPC $> 2.0$.
  \item \textbf{Core 1 (\texttt{mcf}) \& Core 3 (\texttt{omnetpp}):} Two irregular, memory-choked threads whose aggressive hardware prefetchers spew massive volumes of inaccurate, speculative garbage into the shared LLC.
\end{itemize}
In an unmanaged baseline cache, Core 1's prefetcher destroys Core 0 and Core 2. This workload mix is the crucible that proves whether a cache policy can survive real-world multicore interference!

\section{Hardware Prefetching Mechanics \& The Multicore Pollution Crisis}

\subsection{How Does a Hardware Prefetcher Actually Work?}
A hardware prefetcher is a dedicated hardware state machine monitoring memory access addresses issued by the processor core.
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Next-Line Prefetcher:} The simplest prefetcher. Whenever line $N$ is requested, it unconditionally requests line $N+1$.
  \item \textbf{Instruction-Pointer Stride Prefetcher (IP-Stride):}
  \begin{itemize}
    \item Maintains a table indexed by the Program Counter (PC / IP) of load instructions.
    \item For each load instruction, it records: \texttt{Last\_Address} and \texttt{Last\_Stride}.
    \item When the same instruction executes again at address $A_{\text{new}}$:
    \begin{equation}
      \text{Current Stride} = A_{\text{new}} - \text{Last\_Address}
    \end{equation}
    \item If $\text{Current Stride} == \text{Last\_Stride}$ two times in a row, the prefetcher trains state to \textit{Confident}. It immediately issues a speculative memory fetch for:
    \begin{equation}
      A_{\text{prefetch}} = A_{\text{new}} + \text{Stride}
    \end{equation}
  \end{itemize}
\end{enumerate}

\subsection{The Three Universal Metrics of Hardware Prefetching}
Every cache researcher evaluates prefetchers using three formal mathematical metrics:
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Prefetch Accuracy ($A$):}
  What percentage of issued prefetches were actually used by the CPU?
  \begin{equation}
    A = \frac{\text{Useful Prefetch Hits}}{\text{Total Prefetches Issued}}
  \end{equation}
  For \texttt{gcc}, $A > 50\%$. For \texttt{mcf}, $A < 1\%$.

  \item \textbf{Prefetch Coverage ($C$):}
  What fraction of total baseline cache misses were eliminated by prefetching?
  \begin{equation}
    C = \frac{\text{Useful Prefetch Hits}}{\text{Demand Misses} + \text{Useful Prefetch Hits}}
  \end{equation}

  \item \textbf{Prefetch Timeliness ($T$):}
  Did the prefetched line arrive in the cache \textit{before} the CPU requested it?
  \begin{itemize}
    \item If it arrived before $\rightarrow$ Latency is 100\% completely hidden (Cache Hit).
    \item If it is still traveling across the bus when the CPU asks for it $\rightarrow$ \textbf{Late Prefetch} (CPU still stalls, but for fewer cycles).
  \end{itemize}
\end{enumerate}

\subsection{The Multicore Contention Disaster}
In a shared multicore Last-Level Cache, private L2 prefetchers from each core dump their lines into the shared 8MB LLC. Standard replacement policies (LRU and standard SRRIP) are \textbf{prefetch-oblivious}: they treat a speculative prefetch packet identically to a confirmed demand fetch from a CPU register load.

\begin{defensebox}[title=\textbf{The Chain Reaction of Multicore Prefetch Pollution}]
\begin{enumerate}[leftmargin=1.2em]
  \item Core 1 (\texttt{mcf}) has $<1\%$ prefetch accuracy, but its L2 prefetcher aggressively issues hundreds of speculative loads into the memory controller.
  \item These useless lines arrive at the shared LLC and are inserted at high priority (MRU in LRU, $RRPV=2$ in SRRIP).
  \item Because the set is full, the cache controller must evict existing lines.
  \item The lines chosen for eviction are active working set blocks belonging to Core 0 (\texttt{gcc}) and Core 2 (\texttt{perlbench})!
  \item Core 0 and Core 2 suddenly experience severe cache misses on data they were just using.
  \item Core 0 and Core 2's pipelines stall on memory, their ROBs fill up, and their IPC plummets.
\end{enumerate}
\end{defensebox}

\section{Cache Replacement Policies: From Belady's MIN to SOTA}

\subsection{Belady's Optimal Replacement Algorithm (MIN / OPT, 1966)}
László Bélády proved mathematically that to minimize cache misses, the optimal policy must:
\begin{quote}
\textit{Evict the cache line that will not be accessed for the longest period of time in the future.}
\end{quote}
\textbf{Why can't we build Belady's MIN in hardware?} Because it requires a crystal ball! Hardware cannot look hundreds of thousands of cycles into the future to know which memory address the operating system or user program will access next. Every practical cache replacement policy is an engineering approximation of Belady's MIN based on past history.

\subsection{Least Recently Used (LRU) \& Its Fatal Weakness}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Core Premise:} If a line was accessed recently, it will be accessed again soon (\textit{Temporal Locality}).
  \item \textbf{Hardware Cost:} To track exact recency in a 16-way set, hardware must maintain a stack of 16 entries ($16!$ possible permutations). This requires $\approx \log_2(16!) \approx 44$ bits of metadata per set, or complex matrix update logic, consuming significant silicon area and dynamic power on every access.
  \item \textbf{The Scanning / Thrashing Flaw:}
  \begin{itemize}
    \item Suppose a loop touches 17 distinct blocks ($A_0, \dots, A_{16}, A_0, \dots$) in a 16-way set.
    \item Block $A_{16}$ evicts $A_0$. Then the loop requests $A_0$, which misses and evicts $A_1$. Then $A_1$ misses and evicts $A_2$.
    \item \textbf{Hit rate drops to EXACTLY 0.0\%!} LRU experiences catastrophic thrashing whenever the working set exceeds cache capacity by even a single block.
  \end{itemize}
\end{itemize}

\subsection{Re-Reference Interval Prediction (RRIP - Jaleel et al., ISCA 2010)}
To overcome LRU's complexity and thrashing vulnerability, Aamer Jaleel and his team at Intel Architecture Research invented \textbf{RRIP}:

\begin{defensebox}[title=\textbf{RRIP Fundamentals}]
Instead of tracking recency order, RRIP predicts the \textbf{Re-Reference Interval} (how soon in the future a line will be referenced again).
\begin{itemize}[leftmargin=1.2em]
  \item Each cache line stores an $M$-bit counter called the \textbf{Re-Reference Prediction Value (RRPV)}.
  \item In standard 2-bit RRIP ($M=2$), the counter takes values in $\{0, 1, 2, 3\}$:
  \begin{itemize}
    \item $RRPV = 0$: \textbf{Near-immediate Re-Reference} (MRU equivalent, safest from eviction).
    \item $RRPV = 1$: \textbf{Short Re-Reference Interval}.
    \item $RRPV = 2$: \textbf{Long Re-Reference Interval} (Standard insertion priority).
    \item $RRPV = 3$: \textbf{Distant Re-Reference Interval} (Victim status; chosen for eviction).
  \end{itemize}
\end{itemize}
\end{defensebox}

\subsubsection{The Three Classic Flavors of RRIP}
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Static RRIP (SRRIP):}
  \begin{itemize}
    \item \textit{Insertion:} Inserts all new incoming lines with $RRPV = 2$.
    \item \textit{Hit:} Promotes the hit line to $RRPV = 0$.
    \item \textit{Eviction:} Scans the set for any line with $RRPV = 3$. If found, evict it. If no line has $RRPV=3$, increment all RRPVs in that set by $+1$ until at least one line reaches 3, then evict that line.
  \end{itemize}

  \item \textbf{Bimodal RRIP (BRRIP):}
  Prevents thrashing in working sets larger than the cache. Inserts most lines (e.g., $31/32$) with $RRPV = 3$ (distant), and a tiny fraction ($1/32$) with $RRPV = 2$ (intermediate). This allows a subset of the working set to "stick" in the cache.

  \item \textbf{Dynamic RRIP (DRRIP - ISCA 2010):}
  Uses \textbf{Set Dueling} to choose between SRRIP and BRRIP:
  \begin{itemize}
    \item Deduces 32 sets dedicated to SRRIP, 32 sets dedicated to BRRIP.
    \item A 10-bit saturating counter (\textbf{PSEL} - Policy Selector) increments on SRRIP misses and decrements on BRRIP misses.
    \item The remaining 8,128 sets follow whichever policy is winning.
  \end{itemize}
\end{enumerate}

\subsection{Signature-Based Hit Predictor (SHiP - Wu et al., ISCA 2011)}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Idea:} Instead of guessing, learn which memory load instructions produce useful cache lines.
  \item \textbf{Mechanism:} Hashes the Program Counter (PC) of the load into a signature. Indexes an \textbf{8,192-entry Signature History Counter Table (SHCT)}.
  \item \textbf{Hardware Cost:} Each SHCT entry is a 2-bit saturating counter.
  \begin{equation}
    \text{SHCT Storage} = 8,192 \text{ entries} \times 2 \text{ bits} = 16,384 \text{ bits} = \mathbf{2,048 \text{ Bytes (2 KB) of dedicated SRAM!}}
  \end{equation}
  \item \textbf{Why This Matters for Your Defense:} SHiP achieves good hit rates, but requires 2 KB of dedicated on-chip SRAM tables, complex hash routers, and training logic. \textbf{Our policy achieves prefetch resilience with ZERO extra bits of SRAM!}
\end{itemize}

\section{Our Proposed Innovation: PA-SRRIP \& PA-Adaptive In-Depth}

\subsection{The Architectural Insight}
Every single prior replacement policy (LRU, SRRIP, DRRIP) suffers from a fundamental architectural flaw: \textbf{they treat incoming cache fills blindly}, ignoring whether the fill originated from an urgent demand miss (a CPU load instruction waiting in the ROB) or an aggressive speculative prefetch issued by an unverified L2 prefetcher.

Furthermore, existing solutions that attempt to solve this (like PACMan or SHiP) add dedicated hardware tables, accuracy estimators, or complex dual queues.

\begin{calloutbox}[title=\textbf{Our Core Design Philosophy}]
We asked a fundamental research question: \textit{Can we design an LLC policy that completely neutralizes multicore prefetch pollution with \textbf{EXACTLY ZERO BITS} of additional hardware storage overhead?}
\end{calloutbox}

\subsection{How Does Hardware Identify Prefetches Without Extra Bits?}
\begin{trapbox}
\textbf{The Senior Professor Interrogation:}\\
\textit{``You claim zero overhead. But how does your cache controller know that an incoming line is a prefetch? You must have added an extra bit to the cache tag directory to store 'is\_prefetch'! If you added a bit, your overhead is not zero! Explain yourself!''}
\end{trapbox}

\begin{answerbox}
\textbf{The Exact Hardware Reality (The Packet Field):}\\
``Sir, in modern computer architectures (including Intel UPI, AMD Infinity Fabric, ARM AMBA AXI5, and ChampSim's \texttt{PACKET} structure), memory requests traveling across on-chip interconnects already carry a protocol header attribute called \textbf{\texttt{access\_type}} (or transaction attribute). 

When a fill arrives from the memory controller or L2 bus, the cache controller inspects this incoming packet bus wire:
\begin{verbatim}
if (packet.type == access_type::PREFETCH) { ... }
\end{verbatim}
This signal is transmitted across the existing interconnect request lines \textbf{at fill time}. \textbf{We do NOT store any prefetch bit in the cache tag directory!} The decision is made dynamically during the insertion cycle. Therefore, the on-chip SRAM storage overhead in the cache tag directory is \textbf{STRICTLY ZERO BITS}!''
\end{answerbox}

\subsection{The PA-SRRIP Policy Specification}
PA-SRRIP operates on standard 2-bit RRPV counters ($M=2$, values $0, 1, 2, 3$). It replaces the blind insertion rule of SRRIP with two clean, hardware-efficient microarchitectural rules:

\begin{defensebox}[title=\textbf{The Two Rules of PA-SRRIP}]
\begin{enumerate}[leftmargin=1.2em]
  \item \textbf{Rule 1: Demoted Initial Insertion (DII)}
  \begin{itemize}
    \item If the incoming line is a \textbf{Demand Miss} (CPU register load waiting in ROB):\\
    $\rightarrow$ Insert at \textbf{$RRPV = 2$} (standard intermediate priority).
    \item If the incoming line is a \textbf{Prefetch Fill} (speculative L2 stream):\\
    $\rightarrow$ Insert at \textbf{$RRPV = 3$} (\textbf{immediate victim status})!
  \end{itemize}

  \item \textbf{Rule 2: Hit-Triggered Promotion (HTP)}
  \begin{itemize}
    \item When a prefetched block sitting at $RRPV=3$ is subsequently requested by the CPU, it scores a \textbf{Cache Hit}.
    \item Upon this hit, the line is promoted to \textbf{$RRPV = 0$} (MRU status).
    \item The line is now treated as \textbf{verified demand data} and is shielded from eviction.
  \end{itemize}
\end{enumerate}
\end{defensebox}

\subsection{The PA-Adaptive Dynamic Controller (0.75 Bytes Overhead)}
While PA-SRRIP provides perfect protection against noisy prefetchers, what happens during program phases where prefetching is highly accurate ($>80\%$)? In those rare phases, demoting all prefetches to $RRPV=3$ might slightly reduce the retention time of useful prefetches before their first hit.

To solve this, we designed \textbf{PA-Adaptive}:
\begin{itemize}[leftmargin=1.5em]
  \item We add a \textbf{single global 6-bit saturating counter} ($0 \dots 63$) for the \textbf{entire 8 Megabyte cache}.
  \item \textbf{Total Hardware Overhead:} Exactly 6 bits $= \mathbf{0.75 \text{ Bytes}}$ for the entire microprocessor!
  \item \textbf{Training Logic:}
  \begin{itemize}
    \item When a prefetch block experiences a demand hit $\rightarrow$ Counter increments by $+1$ (prefetches are proving useful).
    \item When a prefetch block is evicted with 0 hits $\rightarrow$ Counter decrements by $-1$ (prefetches are proving useless).
  \end{itemize}
  \item \textbf{Dynamic Threshold Action:}
  \begin{itemize}
    \item If Counter $\ge 32$ (\textit{High-Utility Phase}): Insert prefetches at $RRPV = 2$ (streaming mode).
    \item If Counter $< 32$ (\textit{Noisy/Contention Phase}): Demote prefetches to $RRPV = 3$ (noise filtering mode).
  \end{itemize}
\end{itemize}

\subsection{Architectural \& Design Alternatives}

\begin{trapbox}
\textbf{Q1: Why not just throttle or turn off the prefetcher when accuracy is low?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Sir, prefetchers operate locally at the private L1 and L2 core level, while cache pollution manifests at the shared L3 / Last-Level Cache across cores. Throttling the prefetcher requires building an accuracy evaluation engine and feedback buses routed backwards across the on-chip interconnect, adding latency, silicon area, and complexity. Furthermore, throttling L2 prefetchers harms core private hit rates. Our policy allows core prefetchers to remain aggressive while the shared LLC filters inaccurate lines locally at zero hardware cost.''
\end{answerbox}

\begin{trapbox}
\textbf{Q2: Why demote to $RRPV=3$ instead of cache bypassing (not inserting the prefetch into LLC at all)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Sir, complete cache bypassing is too destructive. If a prefetch is bypassed and sent directly to L2, it cannot serve any other core, and if the L2 evicts it, it is permanently lost. Demoting to $RRPV=3$ gives the prefetch an \textit{opportunistic probationary trial}: if the CPU needs the block within a few cycles, it scores a hit and is promoted to $RRPV=0$. If it was useless, it is evicted on the next miss. Bypassing eliminates this probationary window entirely.''
\end{answerbox}

\begin{trapbox}
\textbf{Q3: Why use 2 bits for RRPV ($M=4$)? What happens if you use 3 bits ($M=8$)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``In Jaleel et al.'s seminal ISCA 2010 paper, they evaluated $M=2, 3, 4$. They proved that 2 bits ($M=4$, states $0..3$) captures over 95\% of the performance benefits of higher-precision counters. Moving to 3 bits would require 48 bits of storage per 16-way set instead of 32 bits---a 50\% increase in tag array metadata---for less than 0.5\% marginal hit rate gain.''
\end{answerbox}

\begin{trapbox}
\textbf{Q4: Why not use Cache Partitioning (like Intel CAT / Way Partitioning)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Way partitioning statically or dynamically restricts each core to a subset of ways (e.g., Core 0 gets 6 ways, Core 1 gets 2 ways). However, way partitioning reduces the effective cache capacity available to any single core during periods when other cores are idle, causing capacity fragmentation. Our policy provides dynamic, fine-grained protection at the line level without fragmenting cache capacity.''
\end{answerbox}

\begin{trapbox}
\textbf{Q5: Why didn't you implement Drishti (MICRO 2025)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Drishti is an architectural Non-Uniform Cache Architecture (NUCA) and Network-on-Chip (NoC) interconnect framework that dynamically re-routes memory addresses across physical slices using router deflection. ChampSim models a unified LLC without router flit simulation. Our research focuses strictly on the LLC replacement engine, which is complementary to any underlying slicing framework.''
\end{answerbox}

\subsection{Memory Hierarchy, Dirtiness \& Coherence}

\begin{trapbox}
\textbf{Q6: What happens on a dirty line eviction? Does demoting prefetches increase writeback traffic?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Sir, prefetched lines are clean at the time of fill (they were just fetched from memory and have not been modified). If a demoted prefetch sitting at $RRPV=3$ is evicted, it is \textbf{clean}, so it is simply discarded without generating any DRAM writeback traffic! Furthermore, by preventing useless prefetches from evicting dirty demand blocks, PA-SRRIP actually \textbf{reduces} unnecessary DRAM writeback bandwidth.''
\end{answerbox}

\begin{trapbox}
\textbf{Q7: What if a prefetch was dirty? (Trick question!)}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Sir, by definition, an incoming prefetch fill can NEVER be dirty! Prefetches are read operations that load clean data from memory. A cache line only becomes dirty when a store instruction commits a write to that line, which can only happen after the line is accessed by the CPU (at which point our policy has already promoted it to $RRPV=0$!).''
\end{answerbox}

\begin{trapbox}
\textbf{Q8: How does your policy interact with Inclusive vs Non-Inclusive LLCs?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``In our modeled non-inclusive LLC, evicting an inaccurate prefetch from the LLC does not affect private L1/L2 caches. In a strictly inclusive cache, PA-SRRIP is even MORE critical: in an inclusive cache, evicting a demand line from the LLC sends a back-invalidation to L1/L2. By confining prefetch churn to victim slots, PA-SRRIP prevents catastrophic L1/L2 back-invalidation storms!''
\end{answerbox}

\begin{trapbox}
\textbf{Q9: What if Core 0 prefetches a line, but Core 1 accesses it (Cross-Core Sharing)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Our Hit-Triggered Promotion rule triggers on ANY demand hit, regardless of which core issued the demand request. If Core 1 requests the block while it sits at $RRPV=3$, the cache detects a hit, serves Core 1, and immediately promotes the line to $RRPV=0$. The policy handles shared data seamlessly.''
\end{answerbox}

\subsection{Microarchitectural Details \& Corner Cases}

\begin{trapbox}
\textbf{Q10: Doesn't demoting prefetches to $RRPV=3$ hurt useful prefetches in streaming applications?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``No, sir. In streaming workloads like \texttt{gcc}, prefetches are timely---the CPU requests them within a few cycles of arrival. The very first hit immediately promotes them to $RRPV=0$ (MRU). Demoting to $RRPV=3$ only harms blocks that are NEVER accessed by the CPU, which is exactly what we want to evict.''
\end{answerbox}

\begin{trapbox}
\textbf{Q11: What happens if an application changes phases from pointer-chasing to streaming?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``That is precisely why we introduced \textbf{PA-Adaptive}! When the application enters a streaming phase, incoming prefetches begin hitting. Each hit increments the 6-bit counter. Once the counter crosses the threshold ($\ge 32$), the controller automatically switches to inserting prefetches at $RRPV=2$, giving them full intermediate retention.''
\end{answerbox}

\begin{trapbox}
\textbf{Q12: What happens if all lines in a set have $RRPV=3$?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``If multiple lines have $RRPV=3$, the replacement controller simply picks the first one encountered (e.g., lowest way ID). Standard SRRIP priority aging is not needed in that cycle because a valid victim already exists.''
\end{answerbox}

\begin{trapbox}
\textbf{Q13: How does PA-SRRIP handle a scan pattern (streaming through 100MB of data once)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Scan patterns are poison to LRU because 100MB of single-use data permanently flushes the cache. In PA-SRRIP, if the scan is prefetched, lines enter at $RRPV=3$ and are immediately discarded on subsequent misses, completely protecting existing cache blocks from the scan!''
\end{answerbox}

\begin{trapbox}
\textbf{Q14: What about Dead Block Predictors (like PDP)? Why not use that?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Dead block predictors require trace tables or sampling predictors to identify when a block will no longer receive hits. While effective, they require substantial metadata tables (often 4KB to 8KB of SRAM). PA-SRRIP achieves prefetch dead-block protection with zero metadata tables.''
\end{answerbox}

\subsection{Metrics, Simulator \& Rigor}

\begin{trapbox}
\textbf{Q15: What is the exact mathematical definition of Weighted Speedup?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Weighted Speedup is the standard metric for multicore throughput:
\begin{equation}
  \text{Weighted Speedup} = \sum_{i=0}^{N-1} \frac{\text{IPC}_{i}^{\text{shared}}}{\text{IPC}_{i}^{\text{alone}}}
\end{equation}
It measures total system throughput normalized to each application's isolated single-core performance, preventing fast compute threads from artificially dominating slow memory-bound threads.''
\end{answerbox}

\begin{trapbox}
\textbf{Q16: Why not Harmonic Mean IPC?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Harmonic Mean of relative IPCs is used to measure \textit{fairness}, whereas Weighted Speedup measures \textit{system throughput}. In our Week 2 milestone, we are evaluating both Weighted Speedup and Maximum Slowdown to quantify fairness comprehensively.''
\end{answerbox}

\begin{trapbox}
\textbf{Q17: Why did you simulate 20 million instructions and not 1 billion instructions?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``We used pinned SimPoint traces, which are mathematically selected 20M-instruction slices designed to be representative of the entire program's execution. Simulating 20M instructions across 4 cores (80M total instructions) in a detailed cycle-accurate simulator captures steady-state cache behavior while allowing rapid multi-policy exploration.''
\end{answerbox}

\begin{trapbox}
\textbf{Q18: What was your warmup instruction count, and why is warmup necessary?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``We ran 1,000,000 warmup instructions. Warmup is mandatory because when a simulation starts, caches and branch predictors are cold (empty). Without warmup, early accesses experience artificial cold misses that distort steady-state policy evaluation.''
\end{answerbox}

\begin{trapbox}
\textbf{Q19: Can an attacker exploit your prefetch demotion for a microarchitectural side-channel attack (like Flush+Reload)?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Sir, actually PA-SRRIP \textbf{improves} security resilience! Attackers often use speculative prefetch side-channels to prime cache lines. By demoting speculative prefetches to $RRPV=3$, these lines are evicted rapidly before an attacker can measure probe latency, significantly narrowing the side-channel observation window!''
\end{answerbox}

\begin{trapbox}
\textbf{Q20: What is the critical path timing impact of the 6-bit counter in PA-Adaptive?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``The 6-bit counter update occurs completely off the critical timing path. It increments or decrements asynchronously when a fill or eviction event retires, requiring only a simple 6-bit adder. It does not add any gate delays to the 20-cycle LLC tag comparison critical path.''
\end{answerbox}

\begin{trapbox}
\textbf{Q21: What compiler and optimization flags were used for the benchmark traces?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``The SPEC traces were compiled with GCC using \texttt{-O3} optimization flags with standard x86-64 SSE/AVX vectorization, matching standard CRC competition guidelines.''
\end{answerbox}

\begin{trapbox}
\textbf{Q22: What happens if the core prefetchers are completely turned off?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``If core prefetchers are disabled, all memory fills are demand misses ($type == DEMAND$). Under PA-SRRIP, all fills are inserted at $RRPV=2$, which makes the policy behave \textbf{identically to standard SRRIP}. It gracefully degrades to standard SRRIP with zero performance penalty!''
\end{answerbox}

\begin{trapbox}
\textbf{Q23: How does your policy handle Instruction Cache misses vs Data Cache misses?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``Both L1I and L1D misses are demand misses issued on behalf of CPU execution. Therefore, both are inserted at $RRPV=2$. Only speculative prefetch requests from prefetch engines are demoted to $RRPV=3$.''
\end{answerbox}

\begin{trapbox}
\textbf{Q24: What is the silicon area footprint of 0.75 Bytes?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``A 6-bit counter implemented in a 7nm or 5nm standard cell library occupies less than \textbf{30 square micrometers} of silicon area---virtually invisible compared to the millions of square micrometers occupied by an 8MB SRAM array.''
\end{answerbox}

\begin{trapbox}
\textbf{Q25: What is the ultimate one-sentence elevator pitch of your thesis?}
\end{trapbox}
\begin{answerbox}
\textbf{Answer:} ``We prove that shared multicore Last-Level Caches can completely neutralize hardware prefetch pollution with \textbf{zero extra bits of storage} simply by co-designing prefetch-awareness with insertion depth, preserving compute thread IPC while relieving memory stalls.''
\end{answerbox}

\subsection{Slide 2: Motivation \& Multicore Contention (0:30 -- 1:30)}
\textit{[Advance to Slide 2]}

``To motivate our work: Modern CPU cores execute at 4 Gigahertz, while off-chip DRAM takes over 200 clock cycles to deliver data. Hardware prefetchers are deployed in hardware to bridge this memory latency gap by speculatively loading data blocks into the cache before the CPU requests them.

For regular spatial applications like \texttt{gcc}, hardware prefetchers achieve greater than 50\% accuracy, effectively hiding memory latency. However, for irregular, pointer-chasing applications like \texttt{429.mcf}, prefetch accuracy collapses below 1\%.

In a shared multicore Last-Level Cache, standard replacement policies like LRU and SRRIP are prefetch-oblivious: they insert speculative prefetch blocks at the exact same high priority as real demand blocks. Consequently, inaccurate prefetch streams from memory-intensive cores violently evict the active working sets of co-running compute cores, causing severe cross-core contention.

Our central research question is: \textit{Can we design an LLC policy that neutralizes prefetch pollution with ZERO hardware storage overhead?}''

\subsection{Slide 3: Literature Review \& Identified Research Gaps (1:30 -- 2:30)}
\textit{[Advance to Slide 3]}

``During our literature review, we evaluated state-of-the-art cache policies. PACMan from IEEE CAL 2023 uses prefetch-aware dual queues, but requires dedicated tracking counters. DRRIP from ISCA 2010 uses set-dueling PSEL counters, but remains oblivious to whether an access is a demand request or a prefetch. SHiP from ISCA 2011 uses signature-based reuse prediction, but requires an 8,192-entry table consuming over 2 Kilobytes of dedicated on-chip SRAM.

Our identified research gap is that standard high-performance caches cannot afford dedicated SRAM tables solely for prefetch tracking. We need a lightweight mechanism that eliminates prefetch pollution right at insertion with zero hardware storage overhead.''

\subsection{Slide 4: Proposed Architecture: PA-SRRIP \& PA-Adaptive (2:30 -- 4:00)}
\textit{[Advance to Slide 4]}

``Our proposed policy, PA-SRRIP, introduces a dual-mechanism approach requiring zero extra metadata bits:

First, Demoted Initial Insertion: Memory request packets traveling across on-chip interconnects already carry an access-type tag. When a demand miss fills a cache line, we insert it at intermediate priority with RRPV = 2. But when a prefetch fills a line, we demote it to immediate victim status with RRPV = 3. If that prefetch is inaccurate, like in \texttt{mcf}, it sits in the victim position and is evicted on the very next miss without evicting any demand data.

Second, Promotion on Demand Hit: If that prefetch is actually useful, the CPU will request it. Upon this first demand hit, the line is promoted to MRU with RRPV = 0 and converted into verified demand data.

As an extension, PA-Adaptive adds a single 6-bit saturating counter---just 0.75 Bytes for the entire 8MB cache---that monitors aggregate prefetch utility to dynamically toggle between RRPV = 2 and RRPV = 3 based on runtime phase behavior.''

\subsection{Slide 5: ChampSim 4-Core Evaluation (4:00 -- 4:50)}

Under PA-SRRIP, confining pointer noise to victim lines relieves memory contention: Core 1 (\texttt{mcf}) improves by +17.2\% from 0.085 to 0.099 IPC. Compute cores like \texttt{gcc} and \texttt{perlbench} maintain their high IPC of 2.18 and 2.02 without degradation. Overall, we achieve a +6.8\% system-wide weighted speedup with zero hardware storage overhead.''
